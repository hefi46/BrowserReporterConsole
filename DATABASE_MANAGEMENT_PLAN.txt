DATABASE MANAGEMENT INTEGRATION PLAN
Browser Reporter Console - Admin Interface Enhancement
Date: 2025-11-17

OVERVIEW
--------
This document outlines a plan to integrate database size, age, and cleaning
options into the admin menu. The system already has excellent database
infrastructure including a comprehensive stats endpoint and data retention
script. The main work is adding a user-friendly UI to expose these features.


CURRENT SYSTEM STATUS
---------------------
✓ Database statistics endpoint exists: /api/admin/db-stats
✓ Data retention script exists: backend/scripts/data_retention.py
✓ Archive table implemented: visits_archive
✓ Three-tier data lifecycle: Active (0-90d) → Archive (90-365d) → Export/Delete (1y+)
✓ Full-text search indexes on visits table
✓ Schema migrations system in place


DATABASE SCHEMA
---------------
1. users - Browsing data subjects (username, homegroup, email, etc.)
2. visits - Active visit data (0-90 days) with full indexing
3. visits_archive - Archived visits (90-365 days) with minimal indexing
4. dashboard_users - Admin panel users with role-based access
5. schema_migrations - Migration tracking


EXISTING API ENDPOINTS (Admin)
-------------------------------
User Management:
- GET/POST /api/admin/users
- PUT/DELETE /api/admin/users/{username}
- POST /api/admin/users/bulk-import
- GET /api/admin/users/example-csv

Database Statistics (ALREADY IMPLEMENTED):
- GET /api/admin/db-stats
  Returns: total size, connection stats, per-table metrics, record counts,
           activity metrics (24h/7d), oldest/newest visits, index usage

Configuration:
- POST /api/admin/secureconfig
- GET /api/admin/secureconfig/current


IMPLEMENTATION PHASES
=====================

PHASE 1: DATABASE STATISTICS DASHBOARD (Recommended Start)
-----------------------------------------------------------
Risk Level: Very Low (read-only)
Effort: 2-3 hours

Frontend (admin.html):
- Add new "Database Statistics" card in third column layout
- Display metrics from /api/admin/db-stats endpoint:
  * Total database size with visual gauge/progress bar
  * Active visits count (0-90 days)
  * Archived visits count (90+ days)
  * Total record counts
  * Date range (oldest to newest)
  * Last 24h activity (visits, active users)
  * Growth rate indicators
- Add auto-refresh every 30 seconds
- Use Bootstrap 5 cards and Font Awesome icons (already available)

JavaScript:
- Function: loadDatabaseStats()
- Auto-refresh with setInterval
- Visual indicators (green/yellow/red based on thresholds)

Backend:
- No new endpoints needed! Connect to existing /api/admin/db-stats

Security:
- Already enforced via require_admin() decorator


PHASE 2: DATA ARCHIVING CONTROLS
---------------------------------
Risk Level: Low (moves data, doesn't delete)
Effort: 4-5 hours

Frontend (admin.html):
- Add "Data Management Actions" card
- "Archive Old Data" button
  * Shows count of records older than 90 days
  * Confirmation modal: "Archive X records to archive table?"
  * Progress indicator during operation
  * Success message with count and time taken

JavaScript:
- Function: archiveOldData(days)
- Function: previewArchive()
- Modal with confirmation and progress feedback

Backend (new endpoint):
- POST /api/admin/db-archive
  * Parameters: days (default: 90), confirm (bool)
  * Returns: archived_count, time_taken_seconds
  * Implementation: Reuse logic from data_retention.py

Backend (crud.py):
- async def archive_visits_by_date(db, cutoff_date) -> int
  * Move visits from visits table to visits_archive
  * Update visit records with archived_at timestamp
  * Return count of archived records

Security:
- Require admin role
- Confirmation modal
- Audit log entry


PHASE 3: EXPORT & MAINTENANCE OPERATIONS
-----------------------------------------
Risk Level: Medium (deletes after export)
Effort: 5-6 hours

Frontend (admin.html):
- "Export & Delete Old Archives" button (1+ year data)
  * Shows count of archivable records
  * Confirmation: "Export X records to CSV and delete from database?"
  * Progress indicator
  * Download link for exported CSV.gz file
  * Shows freed space estimate

- "VACUUM Database" button
  * Shows reclaimable space estimate
  * Confirmation: "Reclaim disk space? This may take several minutes."
  * Progress indicator
  * Success message with reclaimed space

- "ANALYZE Tables" button
  * Confirmation: "Update query statistics?"
  * Progress indicator
  * Success message with optimization results

JavaScript:
- Function: exportOldArchives(days)
- Function: vacuumDatabase()
- Function: analyzeTables()
- Download handler for CSV.gz files

Backend (new endpoints):
- POST /api/admin/db-export-archive
  * Parameters: days (default: 365), confirm (bool)
  * Creates CSV.gz export file
  * Deletes exported records from visits_archive
  * Returns: export_file_url, exported_count, freed_space_mb

- POST /api/admin/db-vacuum
  * Runs VACUUM on visits and visits_archive tables
  * Returns: reclaimed_space_mb, duration_seconds
  * Note: VACUUM can't run in transaction, may need asyncpg directly

- POST /api/admin/db-analyze
  * Runs ANALYZE on all tables
  * Returns: tables_analyzed, duration_seconds

Backend (crud.py):
- async def export_and_delete_old_archives(db, cutoff_date) -> dict
  * Export to CSV.gz
  * Delete from archive table
  * Return statistics

Security:
- Require admin role
- Double confirmation (preview + confirm)
- Automatic backup suggestion before export
- Audit log entries


PHASE 4: SELECTIVE DELETION TOOLS (Optional - High Risk)
---------------------------------------------------------
Risk Level: High (permanent deletion)
Effort: 6-8 hours

Frontend (admin.html):
- "Delete by Date Range" section
  * Date picker: From date, To date
  * Preview button: Shows count and sample records
  * Delete button (requires double confirmation)
  * Password re-entry for verification

- "Delete by Homegroup" section
  * Dropdown: Select homegroup
  * Checkbox: Include archive table
  * Preview button
  * Delete button (double confirmation + password)

- "Delete User Visits" section
  * Username input/search
  * Shows user's total visit count
  * Preview button
  * Delete button (double confirmation + password)

JavaScript:
- Function: previewDelete(operation, params)
- Function: executeDelete(operation, params)
- Double confirmation modals
- Password verification

Backend (new endpoints):
- GET /api/admin/db-preview-delete
  * Parameters: operation, filters (date_range/homegroup/username)
  * Returns: count, size_mb, date_range, sample_records (5 examples)

- DELETE /api/admin/db-delete-range
  * Parameters: start_date, end_date, confirm_phrase, admin_password
  * Validates password
  * Requires confirm_phrase == "DELETE"
  * Returns: deleted_count, freed_space_mb

- DELETE /api/admin/db-delete-homegroup
  * Parameters: homegroup, include_archive, confirm_phrase, admin_password
  * Returns: deleted_count, freed_space_mb

- DELETE /api/admin/db-delete-user-visits
  * Parameters: username, confirm_phrase, admin_password
  * Returns: deleted_count, freed_space_mb

Backend (crud.py):
- async def get_deletion_preview(db, filters) -> dict
- async def delete_visits_by_date_range(db, start, end) -> int
- async def delete_visits_by_homegroup(db, homegroup, include_archive) -> int
- async def delete_user_visits(db, username) -> int

Security:
- Require admin role
- Preview before delete (show impact)
- Double confirmation modal
- Admin password re-entry
- Typing "DELETE" confirmation phrase
- Audit log entries with admin username
- Rate limiting (prevent accidental repeated deletions)


PHASE 5: DANGEROUS OPERATIONS (Optional - Very High Risk)
----------------------------------------------------------
Risk Level: Very High (potential data loss)
Effort: 3-4 hours

Frontend (admin.html):
- "Clear All Visits" button (dangerous!)
  * Keeps users table intact
  * Deletes all visits and visits_archive
  * Requires typing "CLEAR ALL VISITS" to confirm
  * Admin password re-entry
  * Suggests database backup first

- "Full Database Reset" button (extremely dangerous!)
  * Deletes all data except dashboard_users
  * Requires typing "DELETE ALL DATA" to confirm
  * Admin password re-entry
  * Automatic backup created before operation

Backend (new endpoints):
- DELETE /api/admin/db-clear-all-visits
  * Parameters: confirm_phrase, admin_password
  * Creates automatic backup
  * Truncates visits and visits_archive tables
  * Keeps users table

- DELETE /api/admin/db-full-reset
  * Parameters: confirm_phrase, admin_password
  * Creates automatic backup
  * Deletes all data except dashboard_users
  * Resets ID sequences

Security:
- Require admin role
- Triple confirmation
- Admin password re-entry
- Typing exact confirmation phrase
- Automatic backup before operation
- Audit log entry
- Email notification to all admins

PERFORMANCE CONSIDERATIONS
===========================

Database Size Monitoring:
- Large databases (10GB+) may take time for VACUUM operations
- Consider showing progress indicators for long operations
- Implement timeout handling (max 10 minutes per operation)

Archiving Performance:
- Bulk operations are more efficient than row-by-row
- Use batch sizes of 1000-5000 records
- Show progress percentage during archiving

Export Performance:
- Stream CSV exports for large datasets
- Use compression (gzip) to reduce file size
- Implement chunked downloads for files >100MB

Concurrent Operations:
- Lock tables during maintenance operations
- Prevent multiple simultaneous VACUUM operations
- Queue operations if conflict detected


ROLLBACK PLAN
=============

If Issues Occur During Deployment:
1. Revert admin.html to previous version
2. Disable new API endpoints (comment out routes)
3. Restore from backup if data issues detected
4. Monitor error logs for specific failures
5. Fix issues in development environment
6. Re-test before redeployment

Database Recovery:
1. Always create backup before destructive operations
2. Keep backups for 30 days minimum
3. Test restore procedures monthly
4. Document recovery steps for admins
